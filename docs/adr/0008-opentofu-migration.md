# ADR 0008 — Run OpenTofu in CI, not HashiCorp Terraform

Status: **accepted**.

## Context

The repo has been running two different tools and calling them one thing.

- **CI** ran HashiCorp Terraform **1.9.8**, installed by `dockerfiles/Dockerfile`
  from `releases.hashicorp.com` into the `ci-terraform` image (now `ci-tofu`) as
  `/usr/local/bin/terraform`. No `tofu` binary was in that image.
- **Everything else assumed OpenTofu.** The Makefile's `tf-fmt`/`tf-fmt-check`
  invoke `tofu` directly (and `tf-fmt-check` is deliberately excluded from
  `LINT_TF` with the comment *"it uses tofu, absent from the CI image"*).
  `instance-template/AGENTS.md` documents the instance gate as `tofu fmt`. Every
  tracked `.terraform.lock.hcl` records **`registry.opentofu.org/...`** providers —
  they were generated by `tofu init`, which means they pinned nothing at all
  under Terraform, whose provider addresses are `registry.terraform.io/...`.

The split was invisible because `detect_tf` preferred `terraform`, seven Go call
sites hardcoded `exec.Command("terraform", ...)`, and developers commonly have
`alias terraform=tofu`. A clean local run therefore proved nothing about what CI
executed — the same failure mode as the `~/.terraformrc` `dev_overrides` trap
recorded twice on #343.

It surfaced when a state-encryption change (#354) was written against OpenTofu's
`terraform { encryption { … } }` block, validated locally on OpenTofu 1.12.3, and
would have failed at `init` on all four roots in CI — an outage of every
Terraform operation, not a degraded feature.

## Decision

**Run OpenTofu 1.12.5 everywhere.** `dockerfiles/Dockerfile` installs it into the
`ci-tofu` and `devcontainer` images as `tofu`.

### Installed as `tofu`, with no `terraform` symlink

A drop-in symlink would make the migration invisible and non-breaking, and that
is precisely the reason not to do it: an ambiguous binary name is what let this
situation persist. Anything still invoking `terraform` now fails loudly, and it
fails in the safe direction — the command does not run, so no state is written.

### Resolution order is now `tofu` → `terraform`, in one place per language

- Shell: `detect_tf` in `template-scripts/lib-common.sh` (preference inverted).
- Go: `tfBin()` / `tfCommand()` in `tools/internal/shared/tfbin/tfbin.go`, replacing seven
  hardcoded `exec.Command("terraform", …)` calls.

Both honour `$TF` and resolve in the same order, so a script and `llz` can never
disagree about which binary is running against a given state file. `terraform`
survives only as a **fallback** for adopters mid-migration whose runners still
have just that.

## Migration properties

**State format is shared.** Terraform and OpenTofu both write state format
version 4, and OpenTofu reads state written by Terraform 1.5–1.9 without a format
wall. No state surgery is required; the first `tofu apply` simply re-stamps it.

**The version stamp is the thing to get right.** State records the version that
last wrote it, and a tool refuses state stamped by a version *newer than itself*.
Terraform 1.9.8 stamps `1.9.8`; OpenTofu **1.12.5 > 1.9.8**, so it accepts every
existing state file. Pinning an OpenTofu older than the Terraform that last wrote
would not.

**This is close to a one-way door — state, not config.** Once OpenTofu 1.12.5
writes a state file it is stamped `1.12.5`, and Terraform 1.9.8 will then
*refuse* it as newer than itself. Rolling back means restoring a pre-migration
state snapshot from the bucket, not merely reverting this commit. The
configuration is portable; the state stamp is what pins you.

**Providers move registry.** `registry.terraform.io/linode/linode` becomes
`registry.opentofu.org/linode/linode`. The tracked lock files already record the
OpenTofu addresses, so they start being load-bearing rather than needing to
change — and `make sbom-terraform`, which parses them, starts describing what is
actually installed.

## Consequences

- **Adopter instances with custom Terraform steps break** until they switch to
  `tofu`. That is intended (see the symlink decision) and must be called out in
  the upgrade notes.
- **The image is renamed `ci-terraform` → `ci-tofu`.** An earlier draft of this
  ADR kept the old name, reasoning that renaming would churn `vars.TF_IMAGE` for
  cosmetics. That was wrong on both counts: the name would have been actively
  misleading (grep `terraform`, find an image without it), and the churn is
  avoidable — build-images publishes ONE build under BOTH names for a deprecation
  window, so an un-updated pin keeps resolving to the current image instead of
  silently rotting on the last `ci-terraform` push.

  The alias is signed too. cosign stores a signature as a `sha256-<digest>.sig`
  tag inside the repository it was pushed to, so signing `ci-tofu` does not cover
  `ci-terraform` even though both names resolve to the same manifest.

  The **variable** `TF_IMAGE` keeps its name — it is set in every adopter repo,
  so renaming it would break exactly the instances the aliasing exists to
  protect. Only the image it points at changed.

  A third restatement of the version pin turned up during the rename, beyond the
  two the Dockerfile header names: `ciTerraformTag`, then a package-main const
  beside the `llz tokens` verb and now `versionpins.CITofuTag` in
  `tools/internal/extensions/guards/versionpins/citags.go`,
  which computes the default `TF_IMAGE` for newly scaffolded instances. It was
  still `1.9.8`, so a new instance would have been scaffolded onto a HashiCorp
  Terraform image while every caller invoked `tofu`. It is now `ciTofuTag`. The
  header's "a guard verb is the obvious follow-up" remains the right follow-up,
  and now has three literals to check rather than two.
- #354 (state + plan encryption at rest) is **unblocked** — the `encryption`
  block it needs exists only in OpenTofu, and this is its prerequisite.
- `TF_VERSION` → `TOFU_VERSION`, and the version-named image tags in
  `build-images.yml` and `lint.yml` move to `1.12.5` with it.

## Alternatives rejected

| Option | Why not |
|--------|---------|
| Stay on Terraform, symlink `tofu`→`terraform` | Does not gain the OpenTofu-only features, and keeps the ambiguity. |
| Install OpenTofu **as** `terraform` (drop-in) | Zero-churn, but re-creates exactly the "which tool is this?" confusion that caused the incident. |
| Stay on Terraform, use S3 SSE-C for state encryption | Viable (Linode OBJ supports SSE-C) and reaches a similar at-rest goal — but it covers only objects in the bucket, leaving the uploaded `tfplan.bin` artifacts unprotected, and it needs a bespoke re-encrypt migration with no `fallback` equivalent. Recorded here because it remains the fallback plan if OpenTofu is ever rejected. |

## Verification

- OpenTofu 1.12.5 release artifacts and `SHA256SUMS` confirmed to exist for
  `linux_amd64` and `linux_arm64`, in the same `<sha>  <file>` format the
  Dockerfile's existing `grep | sha256sum --check` step expects — so the
  checksum-verification pattern is unchanged.
- `tfBin()` resolution is unit-tested against a stubbed `PATH` rather than the
  developer's own installation: tofu-preferred, terraform-fallback, `$TF`
  override, resolve-once caching, and "name tofu when neither is present" so the
  error points at the right remedy.
- `make tf-validate-roots`, `tf-fmt-check`, `shellcheck`, `go build`/`vet`/`test`,
  `coverage` all pass.

**Not yet proven:** no real `tofu plan`/`apply` has run against a live state file
in the S3 backend. The first CI run after merge is that proof, and the state-stamp
one-way property above is why the pre-migration state snapshot is worth keeping.
